Agent Memory at Scale:
A Field Guide to the Failure Modes

Every agent framework promises memory. Almost none of them tell you what it costs at a thousand decisions. These are seven failure modes we hit building one — six architectural, one caught only by measurement.

Background

Why agent memory gets more expensive every week

Agent memory today is almost always a transcript: an append-only log of everything that happened, replayed into the context window on every cold start. It works beautifully at ten decisions and quietly becomes the dominant line item at a thousand.

The problem is structural, not an implementation detail. A transcript is linear and can only be replayed. It cannot be queried. So the cost of remembering anything is the cost of re-reading everything, and that cost tracks history rather than relevance. An agent that has been useful for six months is punished for exactly that.

The alternative is to make memory addressable: typed, content-addressed shards behind a constant-size index, so a task loads only what it needs. That single change is what moves recall cost from O(history) to O(relevant shards).

The rest of this page is what went wrong on the way there. Most of these are not obvious, several are invisible until you measure, and one of them — the last — was invisible to us until the benchmark caught it.

💡Everything below is drawn from a working MIT-licensed implementation. Where a claim has a number attached, that number came from bench.run on a pinned model, not an estimate.
Gotcha 01

The prompt-cache mirage

Provider prompt caches are the first thing people reach for when context costs bite, and the savings look enormous in a tight test loop. Then the same system saves nothing in production, and nobody can explain why.

The reason is that cache lifetimes are bounded — on the order of an hour. An agent invoked less often than the cache lives gets zero cross-invocation benefit, no matter how carefully you stabilized your prompt prefix. A daily agent has a cold cache every single run. Cache-stability savings are real only within an invocation, or for agents running more frequently than the TTL.

The measurement error this produces is worse than the missed saving. If you report one blended cost-per-task figure, you have mixed two mechanisms with completely different deployment behaviour, and the blend flatters high-frequency deployments while hiding that low-frequency ones get nothing.

⚠️Consequence: report cold-start cost and within-invocation cache hit rate as separate figures. Never publish a blended number. If a benchmark quotes one number for "cost per task" with caching enabled, you cannot tell which mechanism produced the saving — and neither can its author.
Gotcha 02

Tokenizers are not stable across model generations

A model generation change can shift token counts for byte-identical text by tens of percent. This makes a whole category of published comparison worthless without anyone noticing.

If a benchmark run spans a model change — you started on one generation and the provider rolled forward mid-run — then the delta you measured is the tokenizer, not your architecture. The graph still looks clean. The conclusion is simply about a different thing than you think.

This is especially dangerous for memory benchmarks, because the entire claim is denominated in tokens. A 20% tokenizer shift is the same order as many real architectural wins.

⚠️Consequence: pin one model version for the duration of a run and record it alongside every figure you publish. Treat any model change as a new run, not a continuation. If a number in your README has no model version next to it, you do not know what it measures.
Gotcha 03

Cadence is a deployment property, not an architectural one

It is very natural to design an agent around a loop: wake every N hours, look around, decide. We had exactly that in an early plan, inherited from an unrelated design document, and it was wrong.

Polling a clock makes cost track time instead of opportunity. That is the same failure the whole project exists to fix, just relocated from the context window to the scheduler. An agent that wakes hourly and finds nothing to do has spent real money to learn that nothing happened.

Worse, baking cadence into the substrate makes it un-tunable later. Deployment frequency is something an operator should decide per-environment; if it is an architectural assumption, every consumer inherits your guess.

⚠️Consequence: the substrate should assume no cadence at all. Prefer event-driven triggers. Where you must poll, split it: a cheap watcher model answers only "did anything change enough to wake the expensive one?" and escalates. Cost then tracks events, not the clock.
Gotcha 04

Trust belongs at the read path, not the write path

The moment memory becomes shareable — a registry of known failures, a team's accumulated gotchas — someone proposes gating writes. Reviewed submissions, an allowlist of contributors, a moderation queue. It feels responsible.

It also kills the thing that made the registry worth building. A shared knowledge base is valuable in proportion to how much gets into it; a write gate suppresses exactly the network effect you were trying to create, and it does so silently, because you never see the contributions that were never made.

The alternative is to let writes be unrestricted, attribute every entry to its author, and filter at read time by author reputation and corroboration. Spam still enters the store; it simply never surfaces in a query. You keep the network effect and you get a trust model that each consumer can tune to their own risk appetite.

⚠️Consequence: never add a write gate to fix a trust problem. Fix it in the query client. A write gate is a decision you make once, for everyone, forever; a read filter is a decision each reader makes for themselves.
Gotcha 05

Some fields can never be retrofitted

Two fields belong on every memory record from the very first commit, even though nothing consumes them yet: an encryption envelope and a provenance pointer.

The reason is asymmetric cost. Carrying an unused field is nearly free — a few bytes and a null. Adding one later to an append-only history is impossible, because you cannot rewrite committed records without destroying the append-only property that made the history trustworthy in the first place. History written without provenance can never gain it.

This is the one gotcha on this page that is purely about sequencing. There is no clever recovery, no migration script. You either wrote the field or you have a permanent hole in your record from day one to the day you noticed.

🛑Consequence: before your first commit in any append-only system, ask which fields would be impossible to add later. Carry those from the start even if the features consuming them are two phases away. Everything else can wait.
Gotcha 06

Adoption dies at the fourth core verb

The core surface here is three verbs: commit, recall, prove. That is a constraint, not a current state, and holding it has been harder than any individual feature.

Every genuinely useful capability arrives disguised as a fourth verb. Fork the memory. Export it. Replay a decision. Query the gotchas. Each one is reasonable in isolation, and each one raises the cost of the first ten minutes for every future adopter — the exact window in which most people decide whether to keep going.

The resolution is not to refuse the features but to refuse them core status. Secondary namespace, same code, one import deeper. Adoption cost stays flat; capability keeps growing.

# core: three verbs, forever
from sdk import Memory, Shard
mem = Memory("./mymemory")
root   = mem.commit([Shard(type="gotchas", key="gotcha.x", body={...})])
shards = mem.recall({"type": "gotchas", "contains": "db"})
proof  = mem.prove({"type": "gotchas", "key": "gotcha.x"})

# everything else lives one level down
from sdk.ext import fork, export, import_, replay
💡Consequence: treat the core verb count as a spec-level constant that requires human approval to change, not an implementation detail a refactor can quietly increment.
Gotcha 07 · the measured one

A flat manifest makes recall O(history) again

This is the failure mode that survived design review, survived code review, and was caught only because the benchmark existed.

The whole architecture rests on one claim: recall cost is O(relevant shards), never O(history). We built typed content-addressed shards behind a manifest, measured it — and the addressed-recall arm grew 21× from 10 to 1,000 committed decisions. Flat cost was the entire point, and we did not have it.

The cause was the manifest topology. With a single flat manifest indexing every shard, each new decision adds an entry that every subsequent recall must load — including recalls that have nothing to do with decisions. The shards were addressable; the index in front of them was not. We had rebuilt the transcript one level up and could not see it, because every individual component behaved exactly as designed.

The fix is a two-level manifest: a constant-size root manifest pointing at per-type sub-manifests, so a typed query never loads the index for types it did not ask about. That restored 1.00× growth.

# BEFORE - one index, every recall pays for all history
manifest.json  -> { every shard ever committed }

# AFTER - constant-size root, per-type sub-manifests
manifest.json  -> { gotchas: cid, facts: cid, decisions: cid }
  ↳ gotchas.json    # loaded only for a gotchas query
  ↳ decisions.json  # never loaded by a gotchas query
🛑Consequence: the index loaded on every recall must be constant-size. Addressable storage behind a linear index is still linear — and it will pass every unit test you write, because correctness is unaffected. Only a cost benchmark at increasing history depth exposes it.
⚠️Known residual, stated honestly: recall within a single type is still O(shards-of-that-type). For types whose key count grows without bound, the same class of problem returns at a higher level. That question is open, and it is tracked as open rather than quietly claimed as solved.

Checklist

Auditing your own agent's memory

Whatever you have built or adopted, these are the checks that would have caught the seven failures above. Most take minutes.

  • Plot cost against history depth, not just correctness. Run identical tasks at 10, 100, and 1,000 stored items. If per-task input tokens grow, your recall is O(history) whatever the design doc claims. This is the only check that catches Gotcha 07.
  • Check what your index costs. Whatever structure every recall loads — manifest, catalogue, embedding table header — measure whether it grows with total items. Addressable storage behind a linear index is linear.
  • Pin the model version and record it with every figure. Any number without a model version beside it is unfalsifiable.
  • Report cold-start and cached costs separately. If you can only quote a blended number, you cannot predict what a daily-cadence deployment will cost.
  • Ask which fields you could never add later. In an append-only store the answer is "most of them". Carry provenance and an encryption envelope from the first commit.
  • Count your core verbs. If the first ten minutes require learning more than three operations, measure your drop-off before adding a fourth.
  • Try to corrupt it. Flip a byte in a stored object and re-read. You should get an explicit integrity error, not silently wrong memory. Memory you cannot verify is memory you cannot trust after any incident.
  • Test a cold start with zero session state. An agent should rebuild working context from the index alone. If it needs the transcript, you still have a transcript.
